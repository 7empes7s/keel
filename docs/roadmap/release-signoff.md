# Release sign-off (roadmap task-124)

The sign-off answers one question: **can this candidate build be released, by the evidence
checked in today?** It is generated by `tools/release/readiness.mjs`, never written by hand.
`docs/release/final-acceptance.json` is its JSON output; the tables at the end of this page are
its Markdown output for the same run.

## How to run it

```bash
# The report (JSON, with the recapture plan inside), for one candidate build:
node tools/release/readiness.mjs signoff --build <candidate commit> --accept-objective-gaps \
  [--fixture journeys.json] [--tenant <tenant ref>] --out docs/release/final-acceptance.json
# Only the list of what to recapture at that build:
node tools/release/readiness.mjs recapture-plan --build <candidate commit>
# The tables on this page:
node tools/release/readiness.mjs signoff --build <candidate commit> --accept-objective-gaps --format markdown
# Add --require-ready to exit 1 unless the verdict is ready.
```

The verification key comes from `KEEL_QUALIFICATION_HMAC_KEY` only and is never printed.
The fixture journeys come from `node tools/release/journeys.mjs run` (see
`docs/release/acceptance.md`). `--accept-objective-gaps` applies the 2026-10-09 operator
decision on the eleven objective gaps; they stay listed as unsupported.

## Rules

- **One build.** Every record is judged against the candidate build. A record from another build
  is `other-build`: it decides nothing at the candidate, pass or fail, and goes on the recapture
  list. The Entra writes follow the same rule.
- **Fresh.** 30 days for every record, 7 days for deployed acceptance (`stale` otherwise).
- **Verified.** With the key and tenant, each fresh candidate-build record goes through
  `verifyEvidence` with `--require-live`. Without them it is `unverified`, never qualified.
- **What is judged.** Every gate the code defines: the eleven task-112 ledger gates, one writer
  record per written Wave 2 workload, one read record per Wave 2 workload, the single-record writer
  gates (site grants, site permissions, structure writes, distribution lists, Exchange roles,
  Purview unpublish), ScubaGear, and every registered Entra write (issue #148). The list is derived
  from the gate modules, never hand-kept.
- **Verdict.** `ready` only when a candidate build is named, all six fixture journeys passed, every
  gate and every registered Entra write is `live-qualified`, every objective is live-qualified or
  an accepted gap, and no deferred scope is found shipped. `blocked` when a journey failed, a record
  failed its checks at the candidate build, or deferred scope is declared or found shipped.
  `pending` otherwise. An Entra demotion with no build of its own holds readiness as `demoted`
  (fix, then recapture); it does not block, because the fix may already be in the candidate.
- **Accepted gaps.** Sentinel (task-117) is descoped (decisions 2026-09-30 and 2026-10-04). It is
  listed with its real state and never counted as qualified; a record of it that fails still blocks.
- **Four columns per objective.** Implemented (its boundary tests exist), live-qualified (its gates
  verify at the candidate), manual or unsupported (manual routes and the objective's own gap) and
  deferred. Manual routes (every catalogue type whose decision is `manual`, native recovery routes
  that are not credential-qualified, and Conditional Access enforcement) are never counted as
  automated recovery. The hybrid agent runtime (`engine/contracts/topology.mjs`) is deferred and
  global reference templates are excluded: neither ever counts as shipped, and a runtime entrypoint
  found in the tree blocks the sign-off.

## Limitations

- **No live check.** Nothing here contacts the tenant, the portal or the server. Which build is live,
  and whether the records' signatures verify, **needs the operator**: run the commands above on
  Mulinux with the key.
- **`docs/release/readiness.json`** (task-45, source and deployed revisions) is from 2026-09-15. It
  needs a run on the server (`node tools/release/readiness.mjs` with an operator session); this
  sign-off does not refresh it.
- **Write coverage is per writer record.** The "writer families" list compares the writes in the
  writer records with `WORKLOAD_WRITE_OPERATIONS`. Writes that the task-120 to 123 gates prove are in
  those gates' records and show as missing there.
- **Commands with `[see doc]`** are shortened; the linked doc or tool header has every flag.
- **Mutation checks** (in `engine/roadmap/release-signoff.test.mjs`): skipping missing records,
  counting manual types as automated and marking the hybrid runtime shipped each make the suite fail.
